# Business isolation — first release

New verified users create one Israeli business. Existing records are assigned by migration `b731b9a0c112` to business `00000000-0000-4000-8000-000000000001`. Membership is based on verified Supabase user IDs, never an email allowlist or a client-supplied owner ID. One business per user is enforced for this release.

## Database and rollout

The configured database is already PostgreSQL. Alembic upgrades must be run before restarting the updated backend. The migration preserves records and historical amounts, changes provider/external-ID uniqueness to include business ID, and enables RLS on application tables on PostgreSQL. There are no public API policies: browser-facing Supabase roles must not query these tables directly. The current backend connection uses a privileged database role; all request queries must therefore use the tenant-scoped `get_db` dependency.

An application-table snapshot (schema SQL, JSON records, baseline counts/totals) was stored outside Git under `~/.codex/backups/sydney-expenses/20260913-004804/`. It is not a full Supabase project/Auth/Storage backup. The installed pg_dump 16 cannot dump PostgreSQL 17. For deployment, configure full managed backups and verify a restoration separately.

Assign the preserved business to an existing verified user's Supabase UUID via an explicit administrative operation. Do not auto-claim it by email on login. The local rollout already assigned Ariel's verified UUID. New installations require their own verified owner assignment; an unclaimed legacy business remains inaccessible.

Downgrade is deliberately refused: removing business isolation from multi-business data is unsafe. Restore a verified pre-migration backup if rollback is required.

## Authorization

- Auth user views resolve database membership. The previous email allowlist has been removed.
- `get_db` creates a fresh tenant-scoped session; reads, aggregates, bulk deletes/updates, and ORM writes use central guards in `app/core/tenant.py`.
- `/uploads/` checks that the requested path belongs to a sale in the authenticated business.
- Owners/managers may mutate business records; viewers may read and ask the assistant but cannot mutate records.
- The assistant uses the same scoped session as sales and dashboards.
- Supabase signed document links remain bearer URLs until expiry; do not share them across businesses.

## Current boundaries / next steps

- Self-service setup currently supports Israel, ILS reporting, and Jerusalem time only. Existing per-sale tax treatments and rate snapshots remain intact. International tax rules, arbitrary reporting currencies and timezones are not yet implemented.
- Team invitation, role management UI, and multiple businesses per user are not yet available. Role enforcement and membership storage are implemented.
- Every business can create independent webhook endpoints under `/api/webhooks/connections/{path}`. Three authentication models coexist: `demo-pay` connections are HMAC-signed (secret derived from a server-side master key, shown only at creation/rotation, never stored or returned by list APIs; disabling rejects new events, rotation invalidates the previous secret) and remain development/test-only, blocked from creation and ingestion in production. `grow` connections have no signing capability at all (Grow confirmed `webhookKey` is not a secret) — their URL itself (`url_token`, rotatable independently of the connection's identity) is the only credential, and production additionally enforces Grow's published source-IP allowlist (`GROW_WEBHOOK_ALLOWED_IPS`). `cardcom` connections rely on Cardcom's own server-to-server verification (`LowProfile/GetLpResult`, called with per-connection credentials before any event is trusted) as the real authentication — the connection's `url_token` and production's `CARDCOM_WEBHOOK_ALLOWED_IPS` allowlist are defense-in-depth on top of it, not a substitute. The legacy `/api/webhooks/payments` endpoint remains for compatibility and is assigned exclusively to the preserved business.
- New owners select their payment providers while creating the business. The selection is stored in `business_payment_providers`; the connections page exposes only those providers, and connection creation enforces the same allowlist on the backend. Later additions are restricted to the platform administration API rather than trusting the browser UI.
- Platform authorization is stored in `app_accounts.system_role`. Admin access is never inferred from an email address in request or frontend code. The rollout migration assigns the verified Supabase identity for `arielperl999@gmail.com` the `admin` role, while every other verified identity defaults to `user`. Admin queries leave tenant scope only after that DB role is verified, and the admin UI can list businesses, add a supported provider, and delete a business with exact-name confirmation; it cannot delete its own active business.
- Every Grow, Cardcom, and demo-pay webhook delivery is durably recorded in a business-scoped `webhook_events` inbox row before/around Sale creation — for Grow because it never retries a failed delivery, for Cardcom because verification happens after receipt and durable recording must never depend on that verification succeeding. See README's "Grow connection" and "Cardcom connection" sections and `app/models/webhook_event.py`. A delivery rejected outright (bad content type, malformed payload, IP not allowed, verification failed) is recorded with a dedicated `rejected` status, distinct from a `failed` Sale-creation error, so the two causes are never conflated in the owner-visible activity view.
- Each Cardcom connection's own API name/password are stored encrypted at rest (Fernet, `CARDCOM_CREDENTIAL_ENCRYPTION_KEY`) in a separate `cardcom_credentials` table (`business_id`-scoped like every other table here), decrypted only in-process to make the `GetLpResult` call, and never returned by any API response after creation.
- `demo-pay` is still a fictional provider payload; Grow and Cardcom are both real, production-allowed providers, fully isolated from each other (separate adapters, separate credential handling, separate status mapping) and from `demo-pay`.
- Grow's separate "Invoice creation" webhook (automatic customer-document sync) durably queues in its own `provider_document_events` table — `business_id`-scoped (`BusinessOwned`) like every other table here, plus a unique `(connection_id, external_transaction_id)` constraint that is the *only* way a document can ever be matched to a sale: never by transaction id alone, so a Grow `transactionCode` collision across businesses, or across two connections of the same business, can never cross-attach a document. Cardcom needs no equivalent table — its document details arrive bundled in the same authenticated `GetLpResult` response already used to verify the payment.
- Customers/services are currently fields on a sale; they inherit its business ownership. There are no independent customer/service tables yet.
